# Feature Summary: Measurable-Driven Surveys & Measurable Matrix Question Type

## Summary

- Adds three related capabilities to the Survey subsystem to support issuing a survey about a Measurable
  (e.g. a "Product") to every Application rated under it, with recipients drawn from the Product's own
  involvements rather than the individual applications:
    1. A new `MEASURABLE_MATRIX` survey question field type — a two-category measurable matrix (row
       category x column category), restricted to measurables already rated against the survey's subject
       application.
    2. Survey run recipients/owners can now be resolved via involvement on the run's **selector** entity
       (e.g. a Measurable used to pick a population of Applications), not just the **target** entity (each
       individual Application) as before.
    3. The existing (previously unused) `survey_instance` qualifier entity is now populated automatically,
       so a bulk-issued instance retains a record of which selector entity (e.g. Product) it was issued
       under.
- **Note:**
    - This is a beta feature. We are actively seeking feedback and contributions from the open-source
      community to enhance it.
    - All three changes are additive and backward compatible. Existing survey runs/instances/questions are
      unaffected: `involvementResolutionKind` defaults to `TARGET_ENTITY` (the pre-existing behaviour), the
      qualifier entity is only set on newly-generated instances where the run's selector kind differs from
      the target kind, and `MEASURABLE_MATRIX` is an opt-in field type alongside the existing ones.

## Purpose

- Enable a specific but generically useful pattern: issue one small, atomic survey per Application to the
  people involved with a selector entity (e.g. a Product, or any other Measurable used to group a
  population of applications), asking them to break down where an application is used across two
  independently-configured measurable categories for that selector entity — without bloating a single
  survey with every application's breakdown, and without requiring recipients to hold an involvement on
  each application individually.
- The row/column axes are configured per-question against any two measurable categories at
  template-authoring time - they are not hardcoded to any particular pair of categories, keeping the
  feature generic and applicable to any taxonomy an organisation already models as measurables.

## User-visible behaviour

### Survey run creation — recipients/approvers based on target or selector entity

- New radio toggle on the survey run creation/edit screen: **Recipients/Approvers based on** — `Target
  entity` (default, existing behaviour) or `Selector entity`.
- When `Selector entity` is chosen, the Recipient/Approver Involvement Kind pickers switch to offering
  involvement kinds scoped to the run's *selector* kind (e.g. `MEASURABLE`) instead of the survey
  template's target kind (e.g. `APPLICATION`). The resolved people are shared across every instance
  generated by that run, rather than being resolved individually per target entity.

### Survey instance qualifier

- Survey instances generated by a run whose selector kind differs from the template's target kind (the
  common case for this feature) now carry a `qualifierEntity` — the run's selector entity (e.g. the
  Product). This was already displayed (but always blank) in the "Qualifier" column of the recipient/
  approver panels on the My Surveys screens; it now renders correctly.

### New survey field type: "Measurable Matrix (Beta)"

- Configured in the survey template editor with two measurable category pickers: **Row category** and
  **Column category**.
- In the survey response UI, renders a checkbox matrix: rows and columns are populated only with
  measurables from the configured categories that are **already rated** against the survey's subject
  application (kept small by design — not the full category tree). Ticking a cell records that
  combination as applicable for this application.
- Ratings can be recorded against a measurable at any level of its category hierarchy, but the matrix is
  always rendered - and answered - at the lowest (leaf) level. A rating against a non-leaf measurable is
  transparently expanded to all of its leaf descendants. Each leaf's ancestor chain is rendered as merged
  header cells above/beside the matrix (one header row per column-hierarchy level, one leading column per
  row-hierarchy level) - the ancestor levels themselves are never independently selectable, only the leaf
  cells are.
- "Select all" / "deselect all" checkboxes are available at every level: on a leaf row/column header (all
  columns/rows for that one leaf) and on any merged ancestor header (all leaf rows/columns beneath that
  ancestor, across the full opposite axis) - so a recipient can bulk-answer instead of clicking every
  individual cell.
- Two modes: VIEW (read-only, shows previously checked cells with the same hierarchical headers) and EDIT
  (checkboxes/select-all toggles save immediately, matching the existing Measurable Multi-Select field's
  save-on-check behaviour).
- The response payload also carries the survey instance's qualifier entity (the Product) and its child
  measurables, for a planned future enhancement allowing per-child-product exceptions. This data is
  fetched and stored today but not yet exposed in the matrix UI.

## Data model changes

### `survey_run.involvement_resolution_kind` (new column)

| Column                       | Type            | Nullable | Description                                                                             |
|-------------------------------|----------------:|:--------:|-------------------------------------------------------------------------------------------|
| `involvement_resolution_kind` | VARCHAR/ENUM    |    NO    | `TARGET_ENTITY` (default) or `SELECTOR_ENTITY` — governs how recipients/owners are resolved |

### `survey_instance.entity_qualifier_kind` / `entity_qualifier_id` (existing columns, now populated)

These columns were added in an earlier release for a different, never-completed feature and have always
been readable but never written. They are now populated whenever `SurveyRunService` generates instances
for a run whose selector entity kind differs from the survey template's target entity kind — the value is
the run's selector `EntityReference` (e.g. the Product measurable).

### `survey_question.entity_qualifier_2_id` / `entity_qualifier_2_kind` (new columns)

| Column                     |        Type | Nullable | Description                                                                                    |
|-----------------------------|------------:|:--------:|--------------------------------------------------------------------------------------------------|
| `entity_qualifier_2_id`     |      BIGINT |   YES    | Second qualifier entity id — for `MEASURABLE_MATRIX`, the column category's measurable category id |
| `entity_qualifier_2_kind`   | VARCHAR/ENUM|   YES    | Second qualifier entity kind — always `MEASURABLE_CATEGORY` for `MEASURABLE_MATRIX`                |

The existing single `entity_qualifier_id`/`entity_qualifier_kind` pair (already used by
`MEASURABLE_MULTI_SELECT`) is reused as the **row** category for `MEASURABLE_MATRIX`; the new pair is the
**column** category.

### Survey Response: `survey_question_response.json_response` (existing column, new payload shape)

| Column          |           Type | Nullable | Description                                                                                                    |
|-----------------|---------------:|:--------:|------------------------------------------------------------------------------------------------------------------|
| `json_response` | VARCHAR / TEXT |   YES    | JSON string payload for complex survey responses (used for both `ARC` and `MEASURABLE_MATRIX`).                |

No new response table is required — this follows the same pattern established by the `ARC` field type.

For `MEASURABLE_MATRIX`, the payload is `{"responseType": "MEASURABLE_MATRIX", "selections": [...]}`, where
`selections` has one entry per checked cell (not per question) so each entry is a fully self-describing
record - no further joins are needed to interpret it:

```json
{
  "responseType": "MEASURABLE_MATRIX",
  "selections": [
    {
      "app": {"kind": "APPLICATION", "id": 1, "name": "App 1"},
      "product": {
        "kind": "MEASURABLE", "id": 101, "name": "Product 1",
        "hierarchy": [{"kind": "MEASURABLE", "id": 101, "name": "Product 1"}]
      },
      "row": {
        "category": "Category A", "kind": "MEASURABLE", "id": 201, "name": "Category A - Item 1",
        "hierarchy": [
          {"kind": "MEASURABLE", "id": 210, "name": "Category A - Root"},
          {"kind": "MEASURABLE", "id": 220, "name": "Category A - Group 1"},
          {"kind": "MEASURABLE", "id": 201, "name": "Category A - Item 1"}
        ]
      },
      "column": {
        "category": "Category B", "kind": "MEASURABLE", "id": 301, "name": "Category B - Item 1",
        "hierarchy": [
          {"kind": "MEASURABLE", "id": 310, "name": "Category B - Root"},
          {"kind": "MEASURABLE", "id": 320, "name": "Category B - Group 1"},
          {"kind": "MEASURABLE", "id": 301, "name": "Category B - Item 1"}
        ]
      }
    }
  ]
}
```

- `row`/`column` are named generically (not `capability`/`location`) since the two axes are configured
  per-template against arbitrary measurable categories; each still carries its own `category` (the
  category's display name) so consumers can tell the two axes apart.
- `row`, `column` and `product` are always their **leaf**-level measurable (the level at which a cell is
  actually selectable), each with `hierarchy` giving its full root-to-leaf ancestor path - even when the
  underlying rating, or the survey's qualifier entity, was recorded against a higher (non-leaf) ancestor.
- `app` and `product` are constant across every entry for a given instance (one instance == one
  application, answered in the context of one product) - repeated per entry rather than factored out, so
  each selection stands alone.

## APIs

### `api/survey-question`

| Method | Path                                                                            | Description                                                                                                             | Parameters                              | Returns                       |
|--------|----------------------------------------------------------------------------------|---------------------------------------------------------------------------------------------------------------------------|------------------------------------------|--------------------------------|
| `GET`  | `/api/survey-question/measurable-matrix-data/instance/{instanceId}/question/{questionId}` | For a given survey instance and `MEASURABLE_MATRIX` question, returns the survey's subject application; the leaf row/column measurables (ratings against non-leaf measurables are expanded to their leaf descendants), each with its full root-to-leaf ancestor path; plus the instance's qualifier entity (Product, also resolved to its ancestor path) and its child measurables | `instanceId`, `questionId` (path)        | `SurveyMeasurableMatrixData`  |

### `api/survey-run`, `api/survey-instance`

- No new endpoints. `involvementResolutionKind` is accepted as an additional field on the existing survey
  run create/update payloads; `qualifierEntity` is now populated (previously always null) on
  `SurveyInstance` objects returned by the existing survey instance endpoints.

## Configuration & settings

- None. No new settings keys were introduced for this feature.

## Known limitations / follow-up work

- Per-child-product exceptions (e.g. overriding a checked cell for a specific child of the survey's
  Product) are not yet supported in the UI, though the underlying data (`childProducts`) is already
  fetched and included in the saved response payload to avoid a breaking schema change later.
- `MEASURABLE_MATRIX` is not currently exposed as a Report Grid column (unlike some other question types).
